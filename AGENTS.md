# Repository Guidelines

Rayflow is a Rust workspace (edition 2024) implementing a DAG-based task runtime.
It splits into six core crates: `event` (backend-independent append-only log traits),
`graph` (pure graph primitives), `coordinator` (MySQL-backed leader election),
`runtime` (execution state machine with a MySQL-backed store), and `scheduler`
(actuates graph state and abstracts scheduling destinations), plus `catalog`
(object metadata and logical file names). The `server`, `pilot`, and `agent` directories are binary crates built
on those libraries.

## Project Structure & Module Organization
- `crates/catalog/` — `CatalogSystem` owns metadata GATs and operations; `FileSystem` adds file GATs and operations. Data traits omit row identity and timestamps; owned Toasty models contain them. Catalog `key` and `url` are independently unique `VARCHAR(750)` values. A file has `uuid`, producing `node_run_id` (UUID), `filename`, unique `catalog_uuid`, and timestamps; its path is only the catalog key, with no `file.fullpath`. File upserts match catalog UUID; new rows require a node-run UUID and filename. `get_file` accepts `FileKey::Id` or `FileKey::CatalogKey` and returns the file with its catalog; missing catalogs hide orphaned files. Optional data preserves omitted fields, canonical IDs, and creation times; empty updates preserve timestamps. Persistence uses Toasty operations with transactional Unicode VARCHAR insert workarounds. `ObjectStorage` signs through parameter-carrying `PresignOperation`, with an optional S3 implementation configured explicitly. Directory manifests live in `catalog::directory`, generic path validation in `catalog::path`, endpoint payloads in `server::api::catalog`, and run-scoped key construction in the agent. Upload commit derives ownership from the claimed job and atomically acknowledges the catalog and publishes its file. Agent routes are POST `/api/v1/catalog/{prepare,commit,download}` and `/api/v1/catalog/multipart/{create,upload,complete,abort}`; active claims and run-scoped keys are required. Browser downloads use POST `/api/v1/runs/{run_id}/files/download` for presigning and GET `/api/v1/runs/{run_id}/files/content` for streamed attachments, validate declared ports and pinned producer identities, and require succeeded outputs and uploaded catalogs. Apply migrations 8, 10–13, 17–21; migrations 19–21 assign node-run UUIDs, backfill file ownership, and remove redundant file paths. Unresolved legacy ownership stops migration 21 for explicit mapping before retry. See `doc/catalog.md`.
- `crates/event/` — `Event`, `Emit`, `Read`, `Poll`, and continuous `Reactive` consumer contracts. The always-available `command`, `task`, and `task_event` modules provide MySQL log persistence without depending on `runtime`.
- `crates/graph/` — graph model. `src/lib.rs` defines the `Graph`/`Id`/`GraphStore`/`DraftGraphStore` traits; `src/types.rs` holds node/edge types. Primitives and validation have no I/O. `src/store.rs` implements the store traits directly for Toasty `Db` and `Transaction` through `Executor`; methods take `&mut self`. `graph::models()` registers the versioned `graph` and editable `graph_draft` tables. `load(uuid, None)` selects the highest version; explicit versions are exact matches. Creation and update audit fields are persisted. Publishing inside a transaction uses a savepoint and leaves the outer commit or rollback to the caller.
- `crates/coordinator/` — leader election. `mysql::MySqlLeaderElection` (behind the default `mysql` feature) implements `LeaderElection` and competes for a named, expiring lease in the `leader_election` table; pilots renew it before every consumer pass.
- `crates/runtime/` — command application and execution backend. `src/lib.rs` defines `CommandApply`; `src/backend.rs` holds `Status`; `src/command.rs` owns the `Run` and `NodeRun` models; every new node run has a stable UUID in addition to its numeric primary key, preserved on resume and regenerated on new revisions; scheduler owns `RunConfig` and `NodeConfig`. `src/backend.rs` also provides the MySQL backend; `command.rs` holds run state models and transitions. `Resume` transitions a Pending node to Ready and emits a new task for the same node run; the actuator moves it to Running when creating its job without emitting another task. `TaskEvent::Yield` maps to `Command::Pend` and ends the job as Yielded. MySQL support is unconditional, as in `event`. All log types and polling come from `event`.
- `crates/scheduler/` — `Actuator` (`actuator.rs`) consumes command/task/task-event logs, applies commands, and creates `Job` instances from logical `Task` records that drive the FSM. `Scheduler<B>` (`scheduler.rs`) abstracts job scheduling to agents or external schedulers such as Kubernetes Volcano. `actuator.rs` also owns job and configuration models plus `JobRead`/`JobWrite` persistence contracts. `RunConfig` holds annotation snapshots only; execution version and revision belong to `Run`. New jobs select the latest run config ID and preserve that reference. Apply migration 9 to remove the former config fields and revision uniqueness index. No worker dependency; MySQL support is unconditional.
- `crates/scheduler/src/agent.rs` — `AgentScheduler` fails Polled jobs with `expired_at < now - timeout_gap` and emits Fail events atomically. The default gap is 10 seconds. `ResourceCapacity` is the total agent budget; existing claims reserve resources. New claims and inactive Polled redeliveries reset `expired_at` from the pinned `NodeConfig.lease`. Active jobs are never renewed. Expired jobs are not redelivered or requeued. Terminal events clear ownership while preserving expiry. No registry or queue tables are used.
- `agent/src/transfer.rs` — `JobTransfer` transfers declared artifacts through claim-scoped server endpoints. Inputs, outputs, and transfer checkpoints live under `data_dir/<job_uuid>/`. Large files use S3 multipart and ranged transfers when the server advertises the capability. Completed parts are checkpointed. Ranged downloads validate Content-Range, size, and ETag. Docker mounts inputs read-only at `/data/inputs` and outputs at `/data/outputs`. Directory manifests use `.rayflow-directory.json` and upload last. Provider credentials remain server-owned. See `doc/catalog.md`.
- `pilot/` — leader-elected consumer binary. `src/pilot.rs` renews the leader lease and, while leader, continuously consumes commands, schedules tasks, consumes task events, and applies the resulting commands. `src/config.rs` layers `rayflow.yaml` and `RAYFLOW_PILOT_*` overrides.
- `server/` — axum HTTP API binary. Task-event handlers and app operations live in `job`; graph draft operations live in `graph`. `server::config` owns both `Config` and `StorageConfig`; there are no separate server storage or static graph-store modules. Published graphs come from the database, and `Pilot` defaults to `Db` as its graph store. `/jobs/poll` accepts integer `wait_ms` from zero up to `poll_timeout`; omitted or null waits are randomized in `[poll_timeout / 2, poll_timeout)`. Server settings use `Duration`, deserialized from strings such as `10s` with Jiff. Configure `poll_timeout` (default `30s`, minimum `2ms`) via the config file or `RAYFLOW_POLL_TIMEOUT`. Explicit zero polls immediately. Idle polls retry every `poll_retry_interval` (default `250ms`, minimum `1ms`), configured via the config file or `RAYFLOW_POLL_RETRY_INTERVAL`, with a fresh `AgentRef`, outside completed `App::poll` transactions. Retry sleeps are capped by the request deadline. Never hold database transactions or locks while waiting. Nonempty `active_jobs` always returns after one attempt without extending active job lifetimes.
- `agent/` — execution library and consumer binary. `Agentic` polls sequentially and submits jobs to one `JobManager` per workdir. The manager stages inputs, starts named containers, and reattaches existing containers after restart. Its lifecycle monitor observes container events, enforces leases with exit code 124, and commits required outputs before reporting outcomes. Its usage monitor drains stats independently and finalizes the per-job checkpoints. Each JSON archive has an upload receipt. The cleanup sweep waits for server completion and both receipts before removing local data. The binary loads `Settings` from `rayflow.yaml` (or `RAYFLOW_AGENT_CONFIG` / `RAYFLOW_CONFIG`) plus `RAYFLOW_AGENT_*` overrides, accepts duration strings, and requires a stable `id` UUID. Nested resource overrides use double underscores. Default capacity is host CPU count and total memory. Ctrl-C and SIGTERM leave running containers available for recovery.
- Pilot calls `Actuator::tick_in` and `Scheduler::schedule` inside one leader-protected transaction. The default `AgentScheduler` fails expired jobs after `job_timeout_gap` (default `10s`, configured via `RAYFLOW_PILOT_JOB_TIMEOUT_GAP`). `Pilot::with_scheduler` injects other destinations; external adapters must submit committed requests and reconcile retries after rollback.
- Missing log offsets use configurable `gap_timeout_ms` (10000 by default), wired through `Actuator::with_gap_timeout`. Direct event consumers use matching `event::poll::Config` for `poll_with_config` and `ack_with_config`; `Poll` trait methods retain defaults.
- `server/src/auth/` — optional local/LDAP/OIDC login. Enable `auth.enabled`, initialize providers with `Auth::new` and `App::with_auth`, and apply migrations 7 and 14–16. Auth tables use auto-incrementing numeric primary IDs and unique user/token/state identifiers; the stable identity is `auth_user.user_id`. All API routes enforce sessions or restricted fleet bearer credentials; health stays public. Browser writes require `X-Rayflow-Request: 1`. Audit identity comes from the authenticated user. Nested server auth settings use `RAYFLOW_AUTH__*`; agents use `RAYFLOW_AGENT_AUTH_TOKEN`. See `doc/authentication.md`.
- `rayflow.sql` — MySQL schema (`catalog`, `file`, `graph`, `task`, `run`, `run_config`, `node_config`, `node_run`, `job`, `command_entry`, `task_event`, `poll_offset`, and `leader_election`). Apply it before using the MySQL backend.
- `Cargo.toml` — workspace manifest with shared dependency versions.
- `server/src/app/error.rs` — `AppError` maps application and wrapped domain errors to HTTP statuses and stable `RAYFLOW_*` business codes. JSON failures contain `error_code` and the existing `error` message. `status_code()` and `code()` expose the same mapping to Rust callers.

Tasks are created only when a node run is created or transitions to `Ready`.
`Start`, `Rerun`, `Dryrun`, `Resume`, and successor activation in `Succeed` add
tasks directly without calling `run`. `Run` only transitions `Ready -> Running`.
Actuation consumes the existing task and activates its node without another task.


## Build, Test, and Development Commands
- Use the nightly pinned in `rust-toolchain.toml`; server routes use return-type notation (`S::load(..): Send`) with native async graph store methods.
- `cargo build` — build all crates.
- `cargo check -p runtime` — fast type-check of one crate.
- `cargo check --workspace` — type-check everything.
- `cargo test` — run the test suite.
- `cargo run -p pilot` — run the leader-elected consumer (requires MySQL).
- `cargo run -p agent` — run the container agent (requires a configured `id` UUID and Docker).
- `cargo fmt` — format with rustfmt.
- `cargo clippy` — lint the workspace.

## Coding Style & Naming Conventions
- 4-space indentation; run `cargo fmt` before committing.
- `snake_case` for functions/modules, `CamelCase` for types, `SCREAMING_SNAKE_CASE` for constants.
- Keep graph primitives and validation free of I/O; database logic belongs in persistence modules such as `graph::store`. Keep graph actuation in `Actuator`, resource matching and claims in `AgentScheduler`, and persistence models free of workflow logic.
- Prefer Toasty ORM operations for database access. Use raw SQL only when the ORM cannot express the required behavior, such as MySQL atomic upserts, explicit row locks, or database-clock expressions, and explain the exception in a comment.
- Gate coordinator MySQL code with its `mysql` feature. MySQL support in `event`, `runtime`, and `scheduler` is always available; keep core traits backend-agnostic.

## Testing Guidelines
- Use Rust's built-in harness via `#[cfg(test)]` modules or `crates/<crate>/tests/`.
- Add focused unit tests beside the code they cover and integration tests under `crates/<crate>/tests/`. MySQL integration tests skip unless `DATABASE_URL` is set.
- Name tests after the behavior, e.g. `dryrun_mocks_predecessors`; run with `cargo test -p runtime`.

## Commit & Pull Request Guidelines
- Commit messages use Conventional-Commit style, e.g. `feat(task): mem task`, `feat(trait): core api`. Terse `update` messages appear in history but are discouraged.
- Pull requests: describe the change, list affected crate(s), link related issues, and confirm `cargo fmt`, `cargo clippy`, and `cargo test` pass. Update `rayflow.sql` alongside any storage changes.
